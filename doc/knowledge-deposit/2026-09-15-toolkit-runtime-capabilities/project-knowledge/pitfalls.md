# 设计阶段的关键陷阱

### 1. 不要把 capability 和 libs 按运行进程隔离

- **现象**：把 capability 当作 renderer 代码，把 libs 当作 main 代码。
- **原因**：两者都在 main 运行；真正差异是是否通过 Service/Notice 给 renderer 消费。
- **处理**：capability 可以复用 libs，libs 不依赖 capability；只给 renderer 的完整能力才定义 IPC 契约。
- **状态**：设计确认，2026-09-15。

### 2. 不要为 update 预先制造专属 `libs/update`

- **现象**：围绕当前更新代码拆出只服务 update 的通用层。
- **原因**：下载、完整性、解密、归档、安装器等应从桌面客户端全局角度建设。
- **处理**：update 保留自身组合逻辑，未来选择性复用已经稳定的通用 libs。
- **状态**：设计确认，2026-09-15。

### 3. 不要把流式 Transform 写成整包缓存

- **现象**：Transform 的 `transform()` 只收集 chunk，`flush()` 再一次性处理。
- **原因**：API 看似流式，实际会占用整包内存并阻塞。
- **处理**：SM4 和完整性校验都必须按块/按流处理，支持 backpressure。
- **状态**：设计确认，2026-09-15。

### 4. 不要把 ZIP 内容直接合并到用户传入父目录

- **现象**：新 ZIP 解压后文件覆盖旧文件，同时旧文件残留。
- **原因**：目标参数被误解为最终目录，而实际只是父目录。
- **处理**：最终目录使用 `父目录/ZIP 基础名称`，每个 ZIP 独占目录；替换只影响自身目录。
- **状态**：设计确认，2026-09-15。

### 5. 不要只用字符串黑名单做归档路径防护

- **现象**：只检查路径是否包含 `/`、`..` 或是否是绝对路径。
- **原因**：字符串检查不能证明最终解析路径仍在解压根目录内。
- **处理**：对 `path.resolve(root, entryPath)` 做根目录边界判断；第一版不恢复链接元数据，未知特殊 entry type 才拒绝。
- **状态**：设计确认，2026-09-15。

### 6. 不要让下载器自行决定证书策略

- **现象**：下载器设置 `rejectUnauthorized: false` 或全局接受所有证书。
- **原因**：证书策略属于应用/框架网络配置，下载能力不应覆盖它。
- **处理**：下载器直接使用 Electron `net`，证书策略由上层统一配置；默认失败闭合。
- **状态**：设计确认，2026-09-15。
