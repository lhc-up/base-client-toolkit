# Toolkit 职责与能力建设规则

本文件定义 toolkit 的职责边界、能力分层，以及能力进入 toolkit 的准入规则和建设规则。frame 与业务侧参照执行；跨包争议以本文件为准。

## 1. 职责边界

toolkit 是 Electron 客户端的**可选增强能力包**：提供 IPC 桥接机制（Service / Notice）、窗口增强、主进程通用实现（libs）和 renderer 可直接使用的能力（capability）。

toolkit 的职责是**通用**：解决桌面客户端普遍存在的问题，且能去除具体业务语义。

以下永远不属于 toolkit：

- 业务 manifest、业务接口协议、业务数据格式（如 `describe.json`、`.lj`）
- 业务密钥的获取与派生（toolkit 只提供算法和注入点）
- 业务监管规则、处置策略、登录流程、UI
- 更新策略、资源协议、版本比较策略（业务用 semver 自行组合）

判断口诀：**toolkit 提供动作和机制，业务决定策略和内容。**

## 2. 能力分层

| 层 | 职责 | 消费者 |
|---|---|---|
| `service/` / `notice/` | IPC 桥接机制，唯一承重墙 | capability 与业务 schema |
| `main/capability/` | renderer 可直接使用的一件完整事情（含 serviceSchema / noticeSchema） | renderer |
| `main/libs/` | 主进程通用实现，不直接暴露 renderer | capability 与业务主进程 |
| `main/enhance/` | Electron 既有对象的封装/抽象 | 业务主进程 |
| `shared/` | 三端可加载的纯 JS 基础设施 | 全部 |

归属判定：capability 可复用 libs，libs 不得依赖 capability；专属于某 capability 的逻辑留在 capability 内，不为目录整齐强行下沉；某能力只有动作没有 renderer 契约时归 libs，不硬造 schema。

## 3. 能力准入规则

能力进入 toolkit 不以当前业务消费者数量为门槛，逐项回答以下问题，**全部通过**才具备候选资格：

1. **普遍性**：是否解决桌面客户端普遍存在的问题？
2. **去业务化**：是否能去除具体业务语义（协议、密钥、数据格式、UI）？
3. **契约稳定**：输入、输出、错误、生命周期和安全边界能否写成独立契约？
4. **可测试**：能否脱离具体业务页面和生产服务做单元/集成测试？
5. **演进风险**：进入后是否会绑定业务语义，导致业务变更要发 toolkit 版本？
6. **可维护**：提炼后是否降低整体维护成本，toolkit owner 能否独立维护、版本化和发布？

候选能力先在 toolkit 仓库建立设计与 RED 测试，实现、全量验证、发布后，**必须经项目负责人逐项确认**；确认前不得新增或迁移 package API，业务侧不得先行消费。未通过任一项或未经确认的能力留在业务侧。

## 4. 建设规则

### 4.1 实现规则

- **测试先行**：先写失败测试（RED），再实现到通过（GREEN）；新能力必须含契约测试
- **契约约束**（renderer 面向能力）：
  - Service 只返回可序列化 DTO，不返回带方法的对象
  - 进度、状态、终态只通过 Notice 推送，不提供轮询接口
  - 不向 renderer 暴露绝对路径、密钥或 Node 对象（Stream 等）
  - 文件等持久资源以受控 `scope + fileName` 引用，scope 必须规范化并拒绝逃逸
- **安全边界**：不修改全局证书/代理策略；密钥材料不出主进程；外部输入（URL、路径、归档 entry）必须校验最终解析结果
- **依赖约束**：优先 Node/Electron 原生能力；引入第三方库需评估维护活跃度与体积，optional peer 必须懒加载

### 4.2 注释规范

- 注释只描述当前实现：设计意图、使用方法、坑；简单处不注释
- 禁止引用外部文档章节、记录中间状态、演进过程或已删除内容
- 公开 API 必须带 JSDoc（`@param` / `@returns` / `@throws`）

### 4.3 文档规范

- 设计文档与代码同仓库、同 PR、同版本演进；只保留描述当前最终状态的设计文档
- 不保留决策过程、讨论记录、迁移中间态——历史在 git 里，不在文档里
- README 是用户接触面，架构/能力/治理文档是维护者接触面，内容不重复

### 4.4 发布流程

1. owner 仓库实现 + 全量测试通过 + `npm pack --dry-run` 检查发布内容
2. 按 semver 更新版本；边界变更新增/删除子路径属 breaking change
3. 提交项目负责人确认后，消费方才更新依赖并记录精确版本
4. 消费侧接入后补充消费侧验证，关闭能力登记项
